# 工程证据闭环与可复现交付

## 用途

用于把设计、测试、数据、报告和提交材料组织成可追溯的证据链。
它解决“代码能跑但无法证明有效”“报告数字与比特流不一致”“测试脚本混入最终提交代码”等工程问题。

## 适用条件

- 项目需要同时提交源码、报告、视频和测试数据；
- 存在多个版本、多个比特流或多轮上板测试；
- 需要说明算法有效性、资源优化和失败案例；
- 需要别人从零复现。

## 输入

- 最终 RTL、约束、权重和比特流；
- 测试视频、真实时间窗口和原始记录；
- 时序、资源、功耗和 DRC 报告；
- 历史版本、AI 对话、失败现象和修改记录。

## 工作步骤

1. 建立“最终版本”标签，明确比特流、RTL、权重和报告的对应关系。
2. 把测试分成功能、性能、资源、量化、误报和复现六类，每类只回答一个明确问题。
3. 每组测试保留输入视频、真实窗口、原始记录、分析脚本和结果表。
4. 把结论分成“可以写”“不能写”“需要补证据”三类。
5. 对误报和失败案例做人工复核，不只保留成功样本。
6. 生成文件清单、关键文件哈希和复现步骤。
7. 最终提交目录只保留必要源码、约束、权重和说明，移除仿真脚本、测试视频和历史修改文档。

## 常见问题

| 问题 | 处理方向 |
|---|---|
| 报告数字和最终比特流不一致 | 用最终构建重抓数据，或明确标注历史版本来源 |
| 测试结果无法复现 | 补充视频时间窗口、权重哈希和运行步骤 |
| 同一指标有多种口径 | 统一 TP/FP/FN、时间窗口和评价方法 |
| 失败案例被隐藏 | 保留误报复核和适用范围说明 |
| 最终代码包包含测试脚本 | 分离最终提交代码与完整开发仓库 |

## 验证清单

- [ ] 每个关键数字有来源；
- [ ] 最终比特流有哈希；
- [ ] 测试视频有真实事件窗口；
- [ ] 失败案例和边界已记录；
- [ ] 最终代码包只含必要文件；
- [ ] 复现步骤能从零执行；
- [ ] 报告、图表、视频和代码版本互相一致。

## 边界

本技能是工程验证和交付方法，不能替代算法创新、时序签核或板级安全认证。
